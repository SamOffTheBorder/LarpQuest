# Memory & Context

Phase 4 gives every published chapter a structured memory and makes that memory retrievable, so a 30-chapter story can still recall a detail from chapter 3 without keeping all 30 chapters in the prompt. See [Context Assembly](/architecture/context-assembly) for how the result is rendered into a prompt — this page covers where that material comes from.

## Per-chapter memory generation

On publish, a chapter gets two more artifacts beyond its prose and extracted diffs:

- **Structured summary** — what happened, who was involved, what changed — generated by the `summarizer` role
- **Embedding** — of the *summary*, not the prose, generated by the `embedder` role

Both happen strictly after publication, in a worker that runs out of band — exactly the same guarantee [extraction](/architecture/turn-loop) already gives state updates. A chapter is readable the instant it publishes; memory generation can succeed, fail, or still be pending, and none of that is visible to publication itself.

```
publish_chapter (one transaction)
  -> insert chapters row
  -> enqueue extraction_queue row
  -> enqueue memory_queue row      <- Phase 4

memory worker (out of band, later)
  -> claim_memory_job
  -> summarizer call  -> chapters.summary
  -> embedder call    -> chapters.embedding
  -> chapters.memory_status = 'complete' | 'failed'
```

### `memory_queue` is its own table, not a job type on `extraction_queue`

Summary/embedding generation and state-diff extraction are independent failure domains — one can succeed while the other fails, and each is retried separately. Rather than overload `extraction_queue` with a job-type discriminant, `memory_queue` mirrors its shape exactly (`chapter_id`, `status`, `attempt_count`, `claimed_at`, `last_error`, the same `skip locked` stale-claim recovery). This is the same precedent [Phase 3](/phases/phase-3-research-pipeline)'s `research_jobs` set: a new job kind gets its own table rather than a shared one growing a type column.

`chapters.memory_status` is likewise its own column, separate from `extraction_status` — a failed memory job and a failed extraction are different problems with different urgency, and conflating them into one status would hide that.

## Retrieval

`retrieveRelevantSummaries` embeds the current turn's submissions as a query, then ranks every chapter and arc summary in the story by cosine similarity, returning the top K. It is one function with no branch on universe, genre, or media type — the [context-assembly spec](/architecture/context-assembly) requires this explicitly, and a structural test (`memory/genre-agnosticism.test.ts`) guards it the same way [Phase 2](/phases/phase-2-universe-system)'s engine-wide scanner does.

Similarity search runs through two Postgres functions rather than a plain `.select()`, because PostgREST does not expose the `<=>` cosine-distance operator directly:

```sql
match_chapter_summaries(story_id, query_embedding, k)  -- recent-granularity
match_arc_summaries(story_id, query_embedding, k)      -- distant-granularity
```

Both are scoped to `story_id` inside the query itself, not only by RLS, so retrieval can never rank across stories by omission. Results from both are merged, re-sorted by similarity, and capped at K.

### Retrieval bias is a prompt instruction, not a ranking strategy

A universe's `context_policy.retrieval_bias` (`precedent | information | emotional | thematic`) does not change how similarity search works. It changes what the *summary itself emphasizes* when it's generated — the summarizer prompt gets a bias-specific instruction ("emphasize precedent-setting outcomes," "emphasize what was revealed," and so on) before the chapter is ever published. By the time retrieval runs, every universe uses the identical cosine-similarity code path; what differs is which summaries were written to be found.

This keeps the one piece of genre-shaped behavior in this phase — different universes caring about different kinds of history — entirely inside prompt construction, never inside the engine's retrieval logic.

## Arc compaction

Beyond 50 chapters, one arc summary is generated per closed 12-chapter arc, built from that arc's chapter summaries (not full prose). Retrieval then draws on two granularities: chapter summaries for recent history, arc summaries for anything older.

```
shouldCompactArc(currentTurnNumber) -> { fromChapter, toChapter } | null
```

A pure function of the chapter count — no database read — so every boundary is directly testable. It piggybacks on the same worker that just generated the triggering chapter's own memory, rather than needing a separate scheduled sweep: after a chapter's summary/embedding succeed, the worker checks whether that chapter closed an arc and, if so, generates the arc summary inline. An arc-summary failure never turns the chapter's own memory job into a failure — the chapter's summary and embedding are already persisted by that point.

This keeps assembled context roughly constant as a story grows, instead of growing linearly with chapter count.

## Context policy

Retrieval and compression are tuned per universe *version*, immutable exactly like `entity_schema` — a story pins a version, and its context behavior should be pinned with it:

```json
{
  "recent_chapters": 3,
  "retrieved_chapters": 5,
  "retrieval_bias": "precedent",
  "canon_compression": "full",
  "token_budget": 24000
}
```

A universe version created before this column existed, or a story with no pinned universe at all, resolves to these same defaults — Phase 1's unconstrained behavior is preserved exactly, not treated as a migration path every story eventually takes.

### Canon compression happens once, at publish, not per turn

When `canon_compression` is `summary` or `rules_only`, `assembleContext` reads a pre-computed representation stored on the universe version — it does not run a compression model call on every turn. Both compressed variants are generated synchronously inside `publish_universe_version`/`create_universe_with_version`, before the RPC returns, so a published version is never observed in a partially-compressed state. Universe-version publish is a rare, deliberate action that already follows the multi-minute research pipeline; two more `summarizer` calls are negligible next to that, and the alternative — compressing on every turn — would mean a model call (and its cost and latency) on every single turn instead of once per canon revision.

## Database objects

Created in Phase 4: `memory_queue` (mirrors `extraction_queue`), `arc_summaries` (`story_id`, `from_chapter`, `to_chapter`, `summary`, `embedding`), `chapters.embedding`/`chapters.memory_status`, `universe_versions.context_policy`/`canon_bible_summary`/`canon_bible_rules_only`. New RPCs: `claim_memory_job`, `match_chapter_summaries`, `match_arc_summaries`. The `vector` extension, deliberately deferred since Phase 1, is installed here (moved to a dedicated `extensions` schema per Supabase's advisor guidance, rather than left in `public`).
