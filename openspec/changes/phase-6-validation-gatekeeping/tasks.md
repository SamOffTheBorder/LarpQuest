## 4. Validator loop orchestration

- [x] 4.1 `apps/web/src/lib/engine/validator.ts`: `runValidation(args)` — calls `applicableRules`/`runValidatorCall`/`evaluateRules`, classifies highest severity present (`block` > `warn` > `log`), and returns an outcome (`publish` / `retry` / `fail`) with the flags and, for retry/fail, the blocking rule ids. Deliberately does not touch `turns.status` itself (the caller owns every transition, matching how `generating`'s claim already worked) — see 4.2 for why this split away from the original "runValidation drives the transition" description.
- [x] 4.2 `apps/web/src/lib/engine/turns.ts`: `generateTurn` rewritten as a loop — stream → `generating -> validating` → `runValidation` → branch: `publish` calls `publish_chapter` (now guarded on `validating`, see migration below) with the validation report; `retry` appends `buildBlockRetryAddendum(flags)` to the next attempt's prompt and transitions `validating -> generating` with `attempt_count` incremented, looping; `fail` throws, caught by the existing `markTurnFailed` path. A block-triggered retry happens **within the same `generateTurn` call** (the SSE route sees it as a second round of streamed chunks), not as a new user-triggered `retryTurn` request — the existing `failed`-turn retry stays a separate, manual path for actual generation failures. `buildTurnContext`/`resolveUniverseContext` extended to also return `entities`, `progressionModel`, and parsed `validationRules` (Zod-parsed defensively from the opaque jsonb column, degrading to `[]` on a malformed row rather than throwing mid-generation).
- [x] 4.2b `supabase/migrations/20260821000004_publish_chapter_validating.sql`: `publish_chapter` re-created (drop-and-recreate) with a new `p_validation_report` param and its status guard changed from `generating` to `validating`, since by the time anything calls it now, validation has already run. Not originally scoped as a task — the original plan said "now guarded on validating" without registering that the RPC's guard is a migration, not an application-code change.
- [x] 4.3 `apps/web/src/lib/engine/validator.test.ts`: 10 tests — no-flags publishes; warn-only publishes with the flag in the outcome; `block` retries under the cap (attemptCount 1 and 2, cap 2); `block` fails once the cap is exceeded (attemptCount 3); usage recorded for the validator call; a `canon_exceptions`-suppressed violation does not block; `loadCanonExceptions` row mapping; `buildBlockRetryAddendum` includes only block-severity flags; `toValidationReportJson` shape. `apps/web/src/lib/engine/turns.test.ts`'s shared `callStructured` mock made role-aware (`validator` role returns `{violations: []}`, everything else keeps the existing moderation-shaped `{verdict: 'pass'}`) — all 21 pre-existing tests still pass unmodified otherwise.
