## Why

Phase 5 (Multiplayer) is complete and archived. Part 10 of `STORYFORGE_BUILD_PLAN.md` puts Validation & Gatekeeping next. Today the turn loop goes `locked` → `generating` → `published` with no step in between: `universes.validation_rules` (Stage 7 research output) is written by the research pipeline but nothing ever reads it, `chapters.validation_report` is a jsonb column no code populates, the `gatekeeper` model role exists in `apps/web/src/lib/ai/roles.ts` but no call site uses it, `submissions.proposals` captures what a player proposed but nothing evaluates it, and the `proposals`/`canon_exceptions` tables from Part 8.2 do not exist in any migration yet. A player can currently invent an unearned power and the Narrator will simply write it — there is no check and no reasoned in-universe rejection. This is Part 5 of the build plan, and its exit criterion is explicit: "A player proposing an unearned power gets a reasoned in-universe rejection."

## What Changes

- **Rule engine**: a pure function that evaluates a chapter draft against applicable rules — the engine-provided Standard Rule Pack (5.2: dead entities can't act, no simultaneous locations, destroyed stays destroyed, capability gating when a progression model is active, canon facts not contradicted, submitted intent addressed) plus a universe's research-derived `validation_rules` (5.3, `applies_when` filtered by the universe's `progression_models`). Each rule carries a `severity` of `block | warn | log`. Rule evaluation is data-driven off `validation_rules` and `progression_models` — the engine never branches on which universe or genre is running.
- **Validator loop wired into the turn state machine**: a new `validating` status inserted between `generating` and `published`. `block` severity triggers regeneration with the violation appended to the Narrator prompt, capped at 2 retries, then the turn transitions to `failed` and escalates to GM rather than looping forever (mirrors the existing retry-then-typed-error pattern used for AI structured output). `warn` severity allows publication but stores the flag in `chapters.validation_report` for visible display. `log` severity is recorded silently in the same report, never blocking or surfacing prominently. Every validator call declares role `validator`, resolves its model from `stories.model_config`, is Zod-parsed, and writes a `usage_log` row even when the call fails.
- **Gatekeeper**: evaluates a player's proposal (from `submissions.proposals`) for a new capability or development against the universe's rules, active progression model, and the entity's current state. Runs the `gatekeeper` role. Output is Zod-parsed into `{verdict: allow | allow_with_limits | reject, reasoning, imposed_limits, suggested_alternative, narrative_cost}` per 5.4, one retry with the parse error appended then a typed error. Every evaluated proposal writes a row to a new `proposals` table (schema exists in Part 8.2, no migration yet). The Gatekeeper's ruling is threaded into the Narrator's context for that turn so a `reject` verdict produces prose that reflects the rejection in-fiction, rather than the Narrator silently going along with the original ask.
- **GM override**: one-click action on a `block`/`warn` validation flag or a Gatekeeper `reject`/`allow_with_limits` verdict, restricted to `owner`/`gm` per the existing `member-roles` capability. Writes a new `canon_exceptions` row (Part 8.2 schema) — it never edits or deletes the original flag or proposal row, matching the append-only, non-destructive pattern used by `entity_history`. The rule engine checks `canon_exceptions` before flagging: an exception scoped to a specific rule + entity + capability combination suppresses only that combination on future turns, not the rule generally.
- **Consistency report view**: a read-only per-chapter and per-story view surfacing `chapters.validation_report` (flags, severities, which rule fired) and the story's `proposals` history (verdicts, reasoning, overrides), with the override action available inline for `owner`/`gm`. Spectators and players get read-only access per existing RLS/role patterns.

## Capabilities

### New Capabilities
- `rule-engine`: pure evaluation of a chapter draft against the Standard Rule Pack and a universe's research-derived `validation_rules`, filtered by `applies_when`/`progression_models`, producing severity-tagged flags. Also owns `canon_exceptions` suppression lookup.
- `validator-loop`: the `validating` turn state, block/warn/log handling, regenerate-with-violation-appended up to 2 retries, escalation to `failed` on exhaustion, and `chapters.validation_report` population.
- `gatekeeper`: proposal evaluation against universe rules + progression model + entity state, Zod-parsed verdict output, the `proposals` table, and threading the ruling into the Narrator's turn context.
- `canon-exceptions`: GM/owner override action that writes a permanent, narrowly-scoped `canon_exceptions` row from either a validation flag or a Gatekeeper verdict, checked by the rule engine and the Gatekeeper before re-flagging the same combination.
- `consistency-report`: read-only per-chapter/per-story view of validation flags and proposal history, with inline override for `owner`/`gm`.

### Modified Capabilities
- `turn-loop`: turn state machine gains a `validating` state between `generating` and `published` (`generating` → `validating` → `published`, `validating` → `generating` on a `block` retry, `validating` → `failed` on retry exhaustion). Publication still cannot be blocked by extraction — validation is a distinct, earlier gate.

## Non-goals

- No turn-mode work beyond the existing `freeform` mode — additional modes (`action`, `scene`, `investigation`, `dialogue`, `montage`) are Phase 7.
- No new progression models beyond the two Phase 2 shipped (`ability_unlock`, `none`) — the Gatekeeper and rule engine must work generically against whatever `progression_models` a universe has registered, via the existing dispatch table, with zero new genre- or model-specific branches in engine code.
- No billing or spend-cap UI changes beyond what's needed to display Gatekeeper/validator `usage_log` rows in the existing cost views.
- No change to `assembleContext`'s signature or Phase 4's retrieval/compaction pipeline — the Gatekeeper ruling is threaded in as an additional prompt input for the current turn, not a new context-pool source.
- No moderation changes — Phase 5's `moderator` role and submission-time moderation pass are untouched.

## Impact

- **Schema**: new migration(s) adding `proposals` (id, story_id, entity_id, proposal, verdict, reasoning, imposed_limits, suggested_alternative, narrative_cost, gm_override, created_at) and `canon_exceptions` (id, story_id, rule_id, scope — entity/capability reference, exception_note, created_by, created_at) per Part 8.2, RLS on both gated through `story_members`; a migration adding the `validating` value to the turns status check/enum and the `generating → validating → published` transition to whatever function/constraint enforces the state machine; population of the previously-unused `chapters.validation_report` column.
- **Code**: new `apps/web/src/lib/engine/rule-engine.ts` (Standard Rule Pack + research-derived rule evaluation + canon-exception suppression), `apps/web/src/lib/engine/validator.ts` (validating-state orchestration, retry/escalate), `apps/web/src/lib/engine/gatekeeper.ts` (proposal evaluation, Zod schema, prompt), `apps/web/src/lib/engine/canon-exceptions.ts` (override write path); `apps/web/src/lib/engine/turns.ts` gains the `validating` transition; `apps/web/src/lib/engine/turn-modes.ts` gains Gatekeeper-ruling injection into the `freeform` prompt template.
- **Model roles**: first production use of the existing `validator` and `gatekeeper` roles.
- **Docs**: new `docs/docs/architecture/validation-and-gatekeeping.md`, `docs/docs/phases/phase-6-validation-gatekeeping.md`, sidebar and data-model/build-order updates.
